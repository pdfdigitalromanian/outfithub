## Key decisions

| Area | Decision | Why |
| --- | --- | --- |
| Repo layout | Two independent npm apps (`apps/backend`, `apps/storefront`) + root convenience scripts | Medusa and Next deploy to different hosts; no cross-package hoisting problems |
| Language | Romanian storefront copy, RON, 21% VAT-inclusive prices | Target market is Romania (Sameday, ANPC). Strings are colocated and easy to translate |
| Data access | All Medusa calls are server-side (RSC / server actions / route handlers) | Tokens stay in httpOnly cookies; no Medusa URL/keys needed in client JS beyond the publishable key |
| Caching | `fetch` cache with tags (`products`, `content`, `seo`, …), 60–900 s revalidation + on-demand purge from backend subscribers | Fast ISR pages that update within seconds of admin edits |
| Resilience | At runtime catalog fetch errors are rethrown (ISR keeps last good page); during `next build` they degrade to empty data | Backend outage never caches empty listings / 404 products; CI builds without a backend |
| Catalog filtering | Full published catalog loaded once (cached), filtered/sorted in-process | Medusa store API can’t filter by option value or sort by calculated price; ideal for boutique catalogs (< few thousand SKUs). For larger catalogs plug in a search engine |
| SEO | Separate `seo` module, entries keyed by resource; generated by subscribers; per-field manual overrides (`manual_fields`) | Auto SEO without losing admin edits; storefront fetches SEO by handle in parallel with the product |
| Integrations | One `integrations` module: AES-256-GCM encrypted credentials, status per provider, per-product channel sync rows, logs | Credentials editable in admin, never returned to browser; each channel isolated |
| Channel sync | Subscriber enqueues one row per enabled channel → processed independently; failures back off exponentially (1 min → 6 h, 8 attempts); nightly full resync; hourly provider status pull | “One provider failing never blocks another or the local publish” |
| Google | Merchant API products_v1 (`productInputs:insert` upsert, delete, processed product issues), service-account JWT auth implemented with Node crypto | Content API for Shopping is retired; no heavy googleapis dependency |
| Meta | Graph `items_batch` (UPDATE with `allow_upsert`, DELETE) + batch status check; Conversions API for Purchase | Current catalog batch API; dedup with browser pixel via `event_id = order id` |
| TikTok | Two separate integrations: Events API 2.0 (pixel + server Purchase) and TikTok Shop Partner API 202309 (OAuth, signed requests, product create/edit/delete, inventory, prices, image upload, webhooks) | They are different products with different credentials |
| Sameday | Fulfillment provider without credentials (validates Easybox `locker_id`); AWB/label/tracking/cancel handled by services using stored credentials | Module providers can’t resolve other modules; courier outages never block creating fulfillments |
| Easybox | Locker list cached in DB (`sameday_locker`, refreshed daily), searchable by text or distance; canonical `lockerId` stored in shipping method data and sent as `lockerLastMile` | Fast search without hitting Sameday per keystroke |
| Payments | System provider = cash on delivery; Stripe Payment Element when keys exist | COD is the most common Romanian payment method; Stripe covers cards/Apple Pay/Google Pay |
| Consent | First-party `oh_consent` cookie, 4 categories, equal-weight Accept/Reject, Google Consent Mode v2 defaults denied, tags loaded only after consent | GDPR / Legea 506/2004 / EDPB guidance |
| PWA | App Router `manifest.ts`, generated icons, hand-written `public/sw.js` (static cache-first, images SWR, navigation network-first + offline page; never caches cart/checkout/account/api) | No build plugin needed; safe for commerce |
| Design | Tailwind v4 tokens (warm paper neutrals, ink, clay accent), Instrument Serif + Geist, soft radii, glass only on floating chrome | Editorial fashion look; AA contrast verified with axe |

## Notes on 21st.dev

The build environment’s network policy blocked 21st.dev, so no components were
pulled from it. UI primitives (sheet/drawer, modal, floating-label fields, chips,
price, cards) were hand-built on Radix primitives in the same style and
normalized to the design tokens in `apps/storefront/src/app/globals.css`.
Components from 21st.dev can be dropped in later; map their colors/radii to the
tokens (`bg-ink`, `bg-paper`, `rounded-lg`, …).

## Module map (backend)

| Path | Purpose |
| --- | --- |
| `src/modules/content` | Key/value site content + Markdown pages |
| `src/modules/seo` | SEO entries with manual override tracking |
| `src/modules/wishlist` | Customer wishlists |
| `src/modules/integrations` | Encrypted credentials, channel sync state, logs, Sameday locker cache & shipments |
| `src/modules/sameday-fulfillment` | Fulfillment provider (home / Easybox / return options) |
| `src/lib/providers/*` | API clients: Sameday, Google auth + Merchant API, Meta, TikTok Events, TikTok Shop |
| `src/lib/channels/*` | Product loader, validation, mappers, sync engine, status refresh |
| `src/lib/seo/*` | Pure SEO generation + application |
| `src/lib/shipping/sameday-service.ts` | Locker sync, AWB create/cancel/track |
| `src/lib/tracking/server-conversions.ts` | Consent-aware Purchase events (Meta CAPI, TikTok, GA4 MP) |
| `src/subscribers/*` | Product lifecycle, inventory, listing SEO, Sameday fulfillment, conversions, emails, cache purge |
| `src/jobs/*` | Channel retries (5 min), status refresh (hourly), nightly resync, Sameday tracking + lockers |
| `src/admin/*` | Admin pages (Integrations, Channel sync, Storefront) and widgets (SEO, channels, Sameday) |
